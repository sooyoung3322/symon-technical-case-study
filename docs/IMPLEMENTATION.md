# 주요 백엔드 구현 사례

SYMON을 1인 개발하며 백엔드와 프론트엔드 전체를 담당했습니다. 이 문서에서는 실시간 처리와 데이터 집계 과정에서 다룬 네 가지 백엔드 구현을 정리합니다. 원본 코드와 내부 명세 대신 처리 흐름과 구현 시 고려한 점을 설명합니다.

## 1. MQTT 수신부터 웹 화면 반영까지

### 처리 흐름

Paho MQTT 클라이언트에 연결·수신 콜백을 등록하고, 구독 목록은 동시 접근 가능한 Set으로 관리했습니다. 연결 전 등록된 대상과 재연결 후 복원할 대상을 이 목록으로 관리하고, 연결 완료 시 재구독하도록 구현했습니다. 재구독 실패 시에는 제한된 횟수 안에서 대기 시간을 늘려 재시도합니다.

수신 콜백에서는 메시지 주소 정보를 바탕으로 웹 구독 대상을 구성하고 `SimpMessagingTemplate`으로 페이로드를 전달했습니다. Vue 화면에서는 STOMP 메시지를 해석해 상태를 갱신하고, 화면 생명주기에 맞춰 구독과 연결을 정리했습니다.

화면 전달과 별도로 JSON을 해석해 마지막 수신 시각을 갱신하고, 기존 감시 작업을 취소한 뒤 새 타이머를 등록했습니다. 일정 시간 수신이 없으면 지연 상태를 처리하고, 수신이 재개되면 복구 상태를 반영합니다. 연결 단절 시에는 감시 타이머를 정리하고 재연결 시 감시 상태를 초기화했습니다.

### 고려한 점

MQTT 연결이 살아 있는 것과 개별 대상의 데이터가 계속 들어오는 것은 다른 상태입니다. 연결 콜백은 재연결·구독 복원을, 수신 타이머는 데이터 지연 감시를 담당하도록 나누었습니다.

실시간 전달 경로는 수신 메시지를 DB에 저장한 뒤 보내는 구조가 아닙니다. 화면 전달 이후 수신 상태를 별도로 해석하며, 지연 감시도 메시지를 받은 대상을 기준으로 시작합니다. 이 구분을 통해 연결 상태, 데이터 수신 상태, 이력 저장을 각각의 책임으로 다뤘습니다.

## 2. 이벤트 이력 저장과 사용자별 알림

### 처리 흐름

HTTP로 입력된 이벤트는 관련 메타데이터와 함께 MyBatis를 통해 관계형 DB에 저장했습니다. 이후 업무 관계를 조회해 수신 대상 사용자를 구하고, Redis의 만료 시간이 있는 조건부 저장 결과에 따라 알림 전송과 사용자별 임시 알림 저장을 처리했습니다.

이벤트 알림에는 직접 WebSocket Handler를 사용했습니다. 사용자와 연결 세션의 매핑을 메모리에 관리하고, 대상 사용자의 열린 세션으로 전송했습니다. 연결 종료와 로그아웃 시에는 매핑을 정리했습니다.

### 고려한 점

이벤트 이력은 남겨야 할 기록이고, Redis 상태는 일정 시간 동안 중복 알림을 억제하기 위한 임시 정보입니다. 따라서 이력 저장을 먼저 처리하고 알림 여부를 판단했습니다. 알림 억제는 이벤트 이력 자체의 중복 제거와는 별개입니다.

관계형 DB 저장, Redis 상태 변경, WebSocket 전송은 하나의 원자적 작업으로 묶이지 않습니다. 이 구현을 설명할 때는 이력의 저장 여부와 사용자에게 알림이 전달되는 범위를 구분합니다. 또한 세션 매핑을 애플리케이션 메모리에서 관리하므로 다중 서버 간 세션 공유는 별도의 설계 과제입니다.

## 3. MQTT 요청·응답과 작업 진행 상태

### 처리 흐름

단건 장치 요청은 **응답 구독 → 요청 발행 → 응답 대기 → 구독 정리** 순서로 구현했습니다. 응답 콜백에서 JSON을 해석해 `CompletableFuture`를 완료하고 구독을 해제합니다. 호출 측은 제한 시간을 두고 기다리며, 타임아웃 시에도 구독을 해제하고 만료 결과를 반환합니다.

파일 작업은 진행 메시지에 따라 상태 기록을 갱신하고 STOMP로 화면에 전달했습니다. 성공 시 객체 저장소의 임시 접근 URL을 결과에 포함하고, 완료·실패 분기에서 응답 구독을 정리했습니다.

### 고려한 점

요청을 발행한 직후 응답이 도착할 수 있어 수신 준비를 먼저 했습니다. 응답을 받는 동작뿐 아니라 대기 시간과 구독 해제까지 요청의 생명주기로 다뤘습니다.

`CompletableFuture`는 MQTT 콜백과 호출 결과를 연결하는 데 사용했습니다. 호출 측에서는 제한 시간을 두고 대기하므로 HTTP 요청 전체가 논블로킹인 구조는 아닙니다. 진행 시간이 있는 파일 작업은 중간 상태를 화면에 전달해 처리 과정을 표시했습니다.

## 4. 누적 데이터 조회와 기간별 집계

### 처리 흐름

스케줄러에서 실행 구분 파라미터를 구성하고 `JobLauncher`로 Spring Batch Job을 실행했습니다. 집계 작업은 Tasklet 기반 Step으로 구성했습니다.

일간 집계는 다음 순서로 처리했습니다.

1. 관계형 DB에서 집계 대상을 조회합니다.
2. 고정 크기 작업 풀에서 대상별 DynamoDB 데이터를 시간 범위로 조회합니다.
3. 후속 페이지가 있으면 이어서 조회하고 데이터를 가공합니다.
4. 결과를 동기화된 목록에 모으고 `Future`로 작업 완료를 기다립니다.
5. 수집한 결과를 MyBatis Mapper로 일괄 저장하고 작업 풀을 종료합니다.

데이터가 없는 대상은 결과 없음 상태로 구분했습니다. 주간·월간 집계는 관계형 DB 계산 결과를 저장하며, 이벤트·이용 이력 집계와 월간 보고서 스냅샷 작업도 구현했습니다. 이 문서에서는 누적 데이터의 상류 적재 경로를 다루지 않습니다.

### 고려한 점

대상별 조회·가공은 병렬로 수행하되 작업 풀의 크기를 제한했습니다. 결과 수집에는 동시 접근을 고려하고, 완료를 기다린 뒤 저장하도록 처리 순서를 구성했습니다. 병렬화에 따른 성능 개선 수치는 별도로 측정하지 않았습니다.

Batch 실행 인스턴스를 구분하는 것과 동일 기간을 재집계할 때 업무 데이터의 중복을 방지하는 것은 다른 문제입니다. 개별 작업의 실패 처리, 전체 완료 판정, 재실행 시 저장 정책은 함께 살펴봐야 할 지점입니다.
