# 실제 구현을 바탕으로 한 백엔드 처리 설명

SYMON에 1인 개발자로 참여해 백엔드와 프론트엔드 전체 개발을 담당했으며 주요 기능 구현과 시스템 연동을 수행했습니다. 아래는 이 구현 경험을 실제 소스의 처리 흐름에 맞춰 정리한 내용입니다.

“구현 흐름”은 활성 코드와 호출 관계에서 확인한 동작입니다. “설계 특징과 기술적 판단”은 구현을 설명하기 위한 기술적 해석이며 당시 선택 이유나 최종 의사결정 권한을 추가로 확정하지 않습니다. 운영 서버·네트워크 인프라 구축은 담당 범위로 주장하지 않습니다. 운영 환경에서의 실행 검증 결과도 포함하지 않습니다.

원본 클래스명·메서드명·API 명세·SQL 대신 역할명으로 설명합니다.

## 1. 주요 계층과 책임

| 논리적 기능 | 구현한 책임 |
| --- | --- |
| 메시지 Controller·MQTT 연결 서비스 | 발행·구독 요청 처리와 클라이언트 구독·응답 콜백 관리 |
| 이벤트 Controller·Service·Mapper | 입력, 관련 정보 저장, 수신 대상 조회, 이력 조회 |
| 대시보드 Controller·Service·Mapper | 사용자 역할·소속 범위를 조건에 반영하고 기간별 데이터 조합 |
| 통계 Controller·Service·Mapper | 보고서 목록·상세 조회와 기간별 보고서 처리 |
| 계정·조직·장치 관리 계층 | 등록·조회·수정과 관련 업무 처리 |
| 인증 사용자 로딩 서비스·Repository | JPA 사용자 조회와 Spring Security 인증 객체 구성 |
| 배치 설정·스케줄러·집계 서비스·Mapper | 주기 실행, 누적 데이터 조회, 집계·저장 |
| WebSocket 설정·전송 처리 | STOMP 구독 전달과 직접 WebSocket 세션별 전송 |

업무 데이터에는 MyBatis 인터페이스와 XML SQL이 사용됩니다. 서비스에서 결과를 가공해 HTTP 응답을 구성하는 구현이 있고, 변경 처리 일부에 트랜잭션 경계가 선언되어 있습니다. 모든 서비스의 응답·예외 처리 규약이 동일하다고 일반화하지 않습니다.

## 2. MQTT 구독과 연결 관리

### 구현 흐름

Paho MQTT 클라이언트에 연결·수신 콜백을 등록합니다. 인증서 기반 연결 자료를 별도 관리 서비스에서 읽어 사용하며 자료의 위치와 구성은 공개하지 않습니다.

구독 대상은 동시 접근 가능한 Set에 기록합니다. 연결 준비 전에 등록한 대상은 연결 완료 시 구독 복구 경로에서 처리됩니다. 연결된 상태에서는 즉시 구독을 시도하는 코드가 있습니다. Set으로 등록 목록을 관리하는 것과 모든 호출이 실제 subscribe를 한 번만 실행하는 것은 구분해야 합니다.

자동 재연결 설정과 연결 완료 콜백의 재구독 처리가 함께 있습니다. 재구독은 제한된 횟수 안에서 대기 시간을 늘리며 재시도합니다. 코드의 대기 증가 형태는 선형이므로 지수 백오프로 표현하지 않습니다. 종료 시 연결 해제도 구현되어 있습니다. 일부 동작에는 실행 환경에 따른 분기가 있습니다.

### 설계 특징과 기술적 판단

연결 재성립과 필요한 구독 복원은 다른 상태입니다. 이 둘을 각각 처리하는 이유와 구독 목록을 동시 접근 가능한 구조로 보관하는 이유를 설명할 수 있습니다. MQTT QoS만으로 애플리케이션의 중복 없는 처리가 보장된다고 주장하지 않습니다.

## 3. 수신 메시지를 웹 구독으로 연결

### 구현 흐름

수신 콜백은 페이로드를 문자열로 해석하고 메시지 주소 일부를 이용해 STOMP 전달 대상을 구성합니다. SimpMessagingTemplate을 사용하며 그룹 단위 대상과 수신 주소 기반 대상에 전송하는 호출이 있습니다. 공개 문서에서는 주소 형식이나 식별 규칙을 재현하지 않습니다.

화면 전달 이후 별도 JSON 해석으로 수신 상태 식별값을 얻어 마지막 수신 시각과 감시 타이머를 갱신합니다. JSON 처리 예외는 해당 경로에서 기록합니다. 따라서 콜백 전체가 저장 완료나 JSON 검증 성공을 조건으로 화면 전송을 수행한다고 서술하지 않습니다.

프론트의 상태 표시 화면에는 WebSocket 위에 STOMP 연결을 만들고 구독 메시지를 해석해 화면 상태에 반영하는 코드가 있습니다. 기존 구독·연결 정리도 확인했습니다. 공통 유틸 파일의 존재만으로 모든 화면이 같은 연결 방식을 사용한다고 판단하지 않았습니다.

### 설계 특징과 기술적 판단

MQTT는 외부 수신, STOMP는 웹 구독 대상 전달을 담당합니다. 서버가 어떤 정보를 해석하고 무엇을 그대로 전달하는지 설명할 수 있습니다. 이 콜백에 수신 메시지의 DB 저장을 임의로 추가하지 않았습니다.

## 4. 연결 단절과 수신 지연 감시

### 구현 흐름

수신 시 기존 예약 작업을 취소하고 새 만료 감시 작업을 등록합니다. 일정 시간 메시지가 없으면 지연 상태로 전환하고, 수신 재개 시 복구 상태를 처리합니다. 상태 변화에 따른 알림과 지연 알림을 모아 전송하는 경로가 있습니다.

연결 단절 때는 기존 타이머를 보류·정리하고, 재연결 때는 감시 상태와 대기 중인 지연 알림을 초기화합니다. 활성 운영 알림 연동과 주석 처리된 후보 호출을 구분했습니다. 주석 상태의 알림 채널은 동작 기능으로 소개하지 않습니다.

### 설계 특징과 기술적 판단

메시징 연결 단절과 특정 생산자의 수신 지연을 구분해야 합니다. 소스는 연결 이벤트와 개별 수신 이벤트를 서로 다른 입력으로 감시에 반영합니다. 수신한 대상을 기준으로 타이머가 예약되므로 모든 미수신 대상을 시작부터 감시하는 체계까지 구현되었다고 확대하지 않습니다.

알림 묶음 처리는 설명할 수 있지만 오탐 감소율이나 운영 장애 감소 수치는 근거가 없어 제시하지 않습니다.

## 5. 이벤트 저장과 직접 WebSocket 알림

### 구현 흐름

HTTP 이벤트 서비스는 관련 메타데이터와 이벤트 이력을 Mapper로 저장합니다. 업무 관계를 조회해 수신 대상을 구하고, Redis의 만료 시간이 있는 조건부 저장 결과에 따라 전송과 사용자별 임시 알림 저장을 수행하는 분기가 있습니다.

이력 저장이 중복 알림 판단보다 앞에 있으므로 “모든 이벤트 중복 저장을 방지했다”고 표현하지 않습니다. 만료 기반 상태는 알림 제어에 사용된 것으로 설명하며 원본 키 구성과 유지 기간은 공개하지 않습니다.

직접 WebSocket Handler는 연결과 사용자의 매핑을 메모리에 관리합니다. 열린 세션과 대상 목록을 확인하고 전송합니다. 연결 종료와 로그아웃에는 매핑 정리 코드가 있습니다. 이 경로는 STOMP를 통하지 않습니다.

### 설계 특징과 기술적 판단

영속 이력, 일시적인 알림 상태, 연결된 사용자에게 보내는 전송은 다른 책임입니다. 관계형 트랜잭션 선언이 Redis와 WebSocket까지 원자적으로 묶는다고 주장하지 않습니다. 전체 경로의 전달 보장과 멱등성은 별도 검증이 필요한 주제입니다.

## 6. 요청·응답과 진행 상태

### 구현 흐름

단건 장치 요청은 응답 구독을 먼저 등록한 뒤 발행합니다. 응답 JSON을 해석하면 CompletableFuture를 완료하고 해당 구독을 해제합니다. 호출 측은 제한 시간을 두고 기다리며, 시간 만료 시 구독 해제와 만료 결과 구성이 있습니다.

이는 비동기 콜백을 동기 요청 결과로 연결하는 방식입니다. CompletableFuture 사용만으로 HTTP 요청 전체가 논블로킹이라고 설명하지 않습니다.

파일 요청은 진행 메시지에 따라 기록을 갱신하고 STOMP로 상태를 전달합니다. 성공 시 객체 저장소의 임시 접근 URL을 결과에 포함하며 완료·실패 분기에 응답 구독 해제가 있습니다. 전달 대상에 사용자 식별값을 반영하지만 이를 근거로 사용자 전용 채널의 접근 통제가 검증되었다고 주장하지 않습니다.

### 설계 특징과 기술적 판단

선행 구독은 발행 직후 빠르게 도착하는 응답을 받을 준비입니다. 제한 시간과 완료 시 구독 정리는 대기 자원 생명주기를 설명하는 소재입니다. 동시 요청 간 완전한 응답 상관관계나 모든 예외에서의 정리 보장을 성과로 제시하지 않습니다.

## 7. 저장소 조회와 기간별 집계

### 구현 흐름

스케줄러는 실행 구분 파라미터를 구성하고 JobLauncher로 Spring Batch Job을 실행합니다. Tasklet 기반 Step이 정의되어 있습니다. 정확한 실행 시각과 내부 작업명은 생략합니다.

일간 집계는 관계형 DB에서 등록 대상을 얻고 고정 크기 작업 풀에서 대상별 DynamoDB 조회와 가공을 수행합니다. 대상과 시간 범위를 지정해 조회하며 후속 페이지가 있으면 계속 가져옵니다. 결과는 동기화된 목록에 모으고 Future로 완료를 기다린 뒤 Mapper로 일괄 저장합니다. 작업 풀 종료도 있습니다.

조회 데이터가 없는 대상에는 결과 없음 상태를 구분하는 분기가 있습니다. 주간·월간 집계는 관계형 DB 계산 결과를 저장합니다. 이벤트 및 이용 이력의 기간별 집계, 월간 보고서 스냅샷 작업도 정의되어 있습니다.

DynamoDB 원시 데이터 적재의 상류 경로는 확인하지 않았으며 이 백엔드의 MQTT 저장 기능으로 포함하지 않습니다.

### 설계 특징과 기술적 판단

외부 조회를 제한된 작업 풀에서 병렬 수행하고 결과를 모아 일괄 저장하는 구조입니다. 동기화 목록은 결과 수집의 동시 접근을 다루고 Future 대기는 저장 시점을 결정합니다. 개별 작업 성공과 배치 전체 완료 판정이 동일하다고 단정하지 않습니다.

실행 구분 파라미터는 Batch 실행 인스턴스 식별 장치입니다. 이것만으로 동일 기간 재실행의 업무 데이터 멱등성이 보장된다고 설명하지 않습니다. 병렬화 속도 개선 수치는 측정하지 않았습니다.

## 8. 인증·권한, 예외와 비동기 처리

Spring Security의 커스텀 인증 제공자, 사용자 로딩 서비스, JPA 사용자 조회, 비밀번호 검증과 로그인 성공·실패 처리가 있습니다. 로그인 후 HTTP 세션에 사용자 정보를 보관하며 업무 서비스는 역할·소속 범위를 조회 조건과 권한 판정에 활용합니다.

인증은 활성 로그인 경로에서 확인한 세션 기반으로 설명합니다. 토큰 의존성이나 주석 코드만으로 JWT 인증을 주요 구현이라 소개하지 않습니다. 권한 계층 이름, 인증 자료 전달 방식, 허용 규칙과 예외 설정은 공개하지 않습니다.

인증 실패·접근 거부 응답, 일부 입력 오류의 HTTP 응답 변환, MQTT 파싱·연결 오류 기록, 배치 작업별 예외 처리가 있습니다. 별도 웹 오류 처리 Controller도 있습니다. 중앙 예외 처리기로 모든 오류를 일관되게 관리한다고 주장하지 않습니다.

비동기 활성화 설정은 있으나 분석한 Java 소스에서 활성 @Async 메서드 호출 경로는 확인하지 못했습니다. 실제 동시 처리는 MQTT 콜백·CompletableFuture, 배치 ExecutorService, 감시 ScheduledExecutorService를 기준으로 설명합니다.

## 9. 프론트엔드 연동과 전체 개발 경험

백엔드 API와 Vue 3 화면을 함께 개발해 데이터 저장·조회와 실시간 표시를 연결했습니다. 상태 화면은 STOMP 수신 결과를 반영하고 이벤트 알림은 직접 WebSocket으로 받으며 파일 작업 화면은 진행 상태를 표시합니다. Vuex 상태 관리, Axios HTTP 연동과 구독·연결 정리를 포함했습니다.

전체 개발 경험에서 설명할 핵심은 데이터 흐름의 경계입니다. 실시간 수신은 화면 반영으로, 이벤트는 이력 저장과 대상별 알림으로, 누적 데이터는 집계와 조회로 연결했습니다. 단건 요청에서는 선행 구독부터 응답 대기·정리까지, 집계에서는 조회부터 결과 수집·저장까지 다뤘습니다.

이 기술적 정리는 개인 담당 범위와 별개인 검증 범위를 명시합니다. 무손실 전송·완전한 중복 방지·다중 서버 확장성을 입증하거나 정량 개선을 측정한 결과는 포함하지 않습니다. 기술 선택의 최종 결정, 운영 인프라 구축, 확인되지 않은 운영 대응 경험까지 확대하지 않습니다.

## 10. 공개 검토 기준

원본 코드·SQL·설정·실제 메시지를 인용하지 않고 동작을 새 문장으로 설명했습니다. 실제 주소, 식별정보, 스키마, 운영값, 비밀정보, 내부 화면과 리소스를 포함하지 않습니다. 보안 정책 상세와 내부 보안 검토 내용도 제외했습니다.

개인 담당 범위는 개발자 본인이 확인했습니다. 회사의 외부 공개 허가는 별도로 필요하며 Private 저장소 업로드도 외부 제공 범위에 포함해 확인해야 합니다. 공개 검토 전 실행 소스·환경 파일·테스트 데이터·내부 문서를 추가하지 않아야 합니다.
