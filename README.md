# SYMON — 실시간 모니터링 시스템

**개발 형태: 1인 개발**

**담당 역할: 백엔드 및 프론트엔드 전체 개발**

MQTT 기반 상태 수신부터 실시간 웹 화면 전달, 이벤트 저장·알림, 기간별 집계까지 구현한 업무 시스템의 기술 사례입니다. 회사 원본 소스는 보안상 공개하지 않으며, 이 저장소에는 일반화한 기술 문서만 포함합니다.

## 1. 프로젝트 소개

SYMON은 장치 상태를 웹 화면에서 확인하고 발생 이벤트를 기록·조회하며 누적 데이터를 기간별로 확인하는 모니터링 시스템입니다. 백엔드와 프론트엔드를 함께 개발해 외부 시스템 메시지 수신부터 사용자 화면 반영까지 연결했습니다.

수신 즉시 전달할 상태 메시지, 이력으로 남길 이벤트, 기간을 묶어 계산할 통계를 각각 처리합니다. 이 과제 설명은 구현에서 도출했으며 회사의 공식 요구사항이나 사업 성과를 인용한 것은 아닙니다.

## 4. 시스템 구성

애플리케이션의 처리 책임을 다음과 같이 나누어 구현했습니다.

- 실시간 상태: MQTT 수신 → STOMP/WebSocket 전달 → 웹 화면 갱신
- 이벤트: HTTP 입력 → 이력 저장 → 알림 대상 조회 → Redis 상태 판단 → 직접 WebSocket 알림
- 장치 작업: 응답 구독 준비 → MQTT 요청 발행 → 응답 대기 또는 진행 상태 전달
- 통계: 주기 실행 → 누적 데이터 조회·가공 → 집계 결과 저장 → 조회 API와 화면 제공

[아키텍처 문서](docs/ARCHITECTURE.md)의 Mermaid는 처리 책임을 설명하는 개념도입니다. 실제 서버·네트워크 배치를 재현하지 않습니다. 누적 저장소의 상류 적재 경로는 분석 범위에서 확정하지 않았습니다.

## 6. 핵심 백엔드 구현 내용

**메시지 수신과 전달:** MQTT 콜백에서 메시지 주소 정보로 웹 구독 대상을 구성하고 SimpMessagingTemplate으로 전달했습니다. 별도 JSON 해석으로 마지막 수신 시각과 감시 타이머를 갱신합니다. 이 경로가 모든 메시지를 DB에 저장한 후 전송하는 구조는 아닙니다.

**연결 복구와 상태 감시:** 연결 재성립 시 등록한 구독을 복구하는 처리와 수신 때 예약 타이머를 갱신하는 감시를 구현했습니다. 메시징 연결 단절과 개별 데이터의 수신 지연을 별도 입력으로 다룹니다.

**이벤트 처리:** 관계형 DB에 이력을 기록하고 수신 대상을 조회한 뒤 Redis 조건부 저장과 만료를 이용하는 분기에서 알림을 전달합니다. 알림 중복 억제가 이벤트 이력 전체의 중복 제거를 뜻하지는 않습니다.

**장치 요청·응답:** 응답을 먼저 구독한 뒤 요청을 발행하고 CompletableFuture로 응답을 연결했습니다. 제한 시간 만료와 응답 완료 시 구독을 정리하는 처리가 있습니다. 파일 작업은 진행 상태 기록과 STOMP 전달을 연결했습니다.

**집계와 데이터 접근:** 일간 집계에서 대상별 DynamoDB 조회·가공을 고정 크기 작업 풀로 수행하고 Future로 완료를 기다린 뒤 결과를 모아 저장했습니다. 업무 데이터는 MyBatis, 인증 사용자 조회는 JPA로 처리하며 Spring Security와 세션 기반 인증을 연동했습니다.

처리 흐름과 설계 쟁점은 [구현 문서](docs/IMPLEMENTATION.md)에 정리했습니다.

## 7. 프론트엔드 구현 및 연동

Vue 3 웹 화면을 개발하고 백엔드 API와 연동했습니다. 대시보드, 이벤트 이력, 보고서와 관리 기능을 화면에서 사용할 수 있도록 구성했습니다.

상태 화면은 STOMP 구독 메시지를 해석해 화면 상태에 반영합니다. 이벤트 알림에는 직접 WebSocket 연결을 사용하며 작업 진행 상태도 실시간으로 표시합니다. 기존 구독·연결 해제와 화면 생명주기에 맞춘 연결 정리 처리를 포함합니다. Vuex 상태 관리와 Axios HTTP 연동도 사용했습니다.

## 8. 기술적인 설계 특징

- 실시간 상태 전달, 영속 이력, 기간 집계를 서로 다른 처리 흐름으로 다룹니다.
- STOMP 구독 전달과 직접 WebSocket 세션 전송의 책임을 구분합니다.
- 연결 복구와 데이터 지연 감시를 나누고 상태 변화에 따른 알림을 처리합니다.
- 장치 응답 구독, 제한 시간, 완료 처리로 요청 자원 생명주기를 관리합니다.
- 제한된 병렬 조회 후 결과를 모아 저장하며 일·주·월 집계를 연결합니다.

이는 구현에서 읽을 수 있는 특징입니다. 특정 기술의 최종 선택 권한이나 당시 의사결정 이유를 임의로 확정하지 않습니다. 무손실 전송, 완전한 중복 방지, 대규모 트래픽 대응과 성능 개선 수치는 성과로 주장하지 않습니다.

## 9. 개발 경험 및 배운 점

백엔드와 프론트엔드를 함께 구현하며 외부 메시지가 서버에서 처리되어 화면 상태로 반영되는 전체 흐름을 연결했습니다. 같은 실시간 기능이라도 상태 전달, 이벤트 이력, 사용자 알림은 서로 다른 책임으로 다뤄야 한다는 점을 설명할 수 있는 경험입니다.

요청·응답에서는 발행 순서뿐 아니라 선행 구독, 대기 시간, 완료 시 정리까지 함께 다뤘습니다. 집계에서는 페이지 조회, 병렬 결과 수집과 저장 시점을 연결했습니다. 이 구현 경험을 바탕으로 전달 보장과 트랜잭션 범위를 구분해 설명합니다.

이 배운 점은 구현 경험의 기술적 정리입니다. 증빙하지 않은 장애 대응 사례, 성능 향상 수치, 운영 검증 결과는 추가하지 않았습니다.

## 10. 소스코드 비공개 안내

회사 원본 Java·Vue·SQL과 설정, 인증정보, 운영 데이터, 내부 화면·디자인 리소스는 보안상 공개하지 않습니다. 실제 주소, 포트 구성, 메시지 주소 체계, DB 스키마, 고객·현장·장치 식별정보와 내부 보안 상세도 제외했습니다.

저장소에는 README.md, docs/ARCHITECTURE.md, docs/IMPLEMENTATION.md, .gitignore만 포함합니다. 시스템 실행이나 운영 접속 없이 정적 소스 분석으로 내용을 확인했으며 개발 기간·사용자 수·성능 개선 수치는 기재하지 않았습니다.

문서는 외부 제공 전 검토용입니다. 저장소 이름과 기술 설명을 포함한 회사의 외부 공개 허가는 별도로 확인해야 합니다. Private 저장소 업로드 역시 회사가 허용하는 외부 제공 범위 안에서 진행해야 합니다.
